# 设计说明与决策记录

## 一、与 MediaCrawler 的关系：库依赖，不是二次修改

`MediaCrawler/` 目录保持**只读、零改动**，本项目 `vspider/` 是独立工程，
通过适配层调用它。这是刻意的决定，理由三条：

1. **上游在活跃维护。** 该仓库 2026 年 6~7 月仍有提交。平台风控天天变，
   小红书签名、抖音参数这类东西失效后靠上游修。一旦改了它的源码，
   后续 `git pull` 必然冲突，等于主动放弃最重要的一份维护红利。
2. **题面要求的是"参考或者使用"，不是"修改"。** 老师原话是
   "具体可参考或者使用 https://github.com/NanmiCoder/MediaCrawler 类似的开源代码实现"。
3. **本次考核的核心能力它根本没有。** 它的抓取类型只有 search / detail / creator
   三种（见 `config/base_config.py` 的 `CRAWLER_TYPE`），完全没有"榜单"概念，
   也没有语音识别、没有内容归纳、没有任务编排。这些不是改几行能补出来的。

我们从它那里取用的是：各平台已签名的 HTTP 客户端、登录态管理、
评论抓取、CDP 反检测浏览器接管。这些是它最有价值的部分。

## 二、改进点：这个项目比"跑通题面两个例子"多了什么

题面给的两个场景（今日榜单前 5、指定用户今日视频）是验收下限。
以下五项是在其之上的实质改进，每一项都对应可演示的功能和可写进报告的设计。

### 改进 1 · 榜单发现层的两级策略抽象

**问题**：题面要求"今天排行榜前 5"，但 MediaCrawler 零覆盖，
而且五个平台的榜单能力极不对等——
B 站有公开免登录的官方排行榜与热门接口；微博有热搜榜和视频社区榜；
抖音、快手只有热搜**词**榜，没有视频榜；小红书连热搜词都拿不到。

**做法**：定义 `RankingProvider` 抽象（`vspider/discovery/base.py`），两级策略：
一级走官方榜单接口，二级降级为"取热词 → 关键词搜索 → 按互动量加权重排"。
每条产出都带 `RankSource` 标注实际走的哪一级，使结果可信度在界面和报告里都透明。

**附带处理的一个歧义**：「今天排行榜前 5」既可理解为"当前榜单快照的前 5 名"
（榜单滚动，视频可能是几天前发布的），也可理解为"今天发布的视频里最热的 5 个"。
`fetch_ranking(today_only=...)` 同时支持两种语义。B 站排行榜是三日综合榜，
单页里当天发布的常常不足 5 条，因此 `today_only=True` 时会自动用热门接口翻页补齐。

### 改进 2 · 多源信息融合，解决"无人声视频"这个致命盲区

**问题**：只做 ASR 的方案在相当大比例的短视频上会直接失效。
小红书尤其明显——大量视频是纯图文轮播或只有 BGM，人声为零，
ASR 返回空字符串，摘要就成了纯粹的编造。

**做法**（`vspider/fusion/context.py`）：五路信号融合——
平台元数据、语音转写、关键帧 OCR（硬字幕）、高赞评论、互动数据。
两个实现细节值得说：

- OCR 结果**按出现顺序去重**。连续帧的硬字幕大量重复，
  不去重会把上下文挤满，把更可靠的标题和转写挤出去。
- 每路信号有**独立字符预算**，且长文本**从中间截断而非砍尾**。
  短视频转写的结尾常有总结句，砍尾会丢掉信息密度最高的部分。

### 改进 3 · 置信度驱动的按需升级

**问题**：全部用便宜快的模型，难例质量不够；全部用贵模型，浪费且慢。

**做法**：提示词强制模型输出 `confidence` 自评，并给出明确校准标准
（转写完整给 0.8 以上；只能靠画面文字和标题给 0.4~0.6；几乎只有标题给 0.3 以下）。
流水线在置信度低于阈值时才升级——换更强的文本模型，并追加视觉模态重做一次。

**已验证这个自评是有效的**：见 `docs/EXPERIMENTS.md` 的 E1，
同一模型在"仅元数据"与"元数据+文稿"两轮之间，置信度从 0.5~0.6 跃升到 0.85~0.9，
说明它确实在反映输入信息的充分程度，可以作为升级触发信号。

### 改进 4 · 可插拔推理后端 + 配置化 profile

**问题**：题面要求"尽量本地部署"，但开发期用本地小模型迭代提示词非常慢。

**做法**：ASR 与归纳都定义抽象基类，实现按配置切换。
关键的省力发现是：vLLM、llama.cpp 的 llama-server、以及各家云端 API
**都实现了 OpenAI 兼容的 `/chat/completions`**，因此归纳层只需要
`OpenAICompatSummarizer` 一个实现即可覆盖三种部署，区别仅在 `base_url` 与模型名。

三套 profile：

- `local` 全本地：SenseVoice(本地) + RapidOCR(本地) + 服务器 vLLM 上的 Qwen3-8B-AWQ
- `api` 增强：SenseVoice(本地) + qwen3-vl-plus(视觉) + qwen-flash / qwen3.8-max
- `cpu` 纯 CPU 演示：SenseVoice(CPU) + RapidOCR + llama.cpp

**交付硬要求：`local` profile 必须能独立跑通全流程**，这是对"本地部署"的正面回答。
`api` 存在的意义是开发期加速迭代，以及作为质量上限的对照组。

### 改进 5 · 可评测性

老师明确说"提交测试通过后，即可进行下一个科研题目"，说明会实测。
因此主动交付 benchmark：成功率、各阶段耗时分解、失败原因分类，
以及 `docs/EXPERIMENTS.md` 里的对照实验数据。

## 三、模型选型与依据

| 环节 | 选择 | 部署 | 依据 |
| --- | --- | --- | --- |
| 语音转文字 | SenseVoice-Small | 本地 | FunASR 官方 184 条中文长音频实测：CPU 上 17.2× 实时、CER 7.81%；同批数据 Whisper-large-v3 在 H100 上仅 13.4× 实时、CER 20.02%。非自回归结构 + 中文专项训练 |
| 长音频切分 | FSMN-VAD | 本地 | SenseVoice 单次前向开销随时长线性增长，不切分会 OOM；同时提供分段时间戳供界面跳转 |
| 画面文字 | RapidOCR | 本地 | onnxruntime 后端，不占显存，CPU 上够快 |
| 画面理解 | qwen3-vl-plus | API | OCR 只能读出画面上的字，读不出画面在发生什么。无字无声的视频只有 VLM 能处理 |
| 归纳 | qwen-flash 默认 / qwen3.8-max 升级档 | API | 见 E1：档位提升收益极小，flash 快 1.5~2.5 倍、便宜 10~50 倍 |
| 归纳（本地） | Qwen3-8B-AWQ + vLLM | 服务器 | 3080Ti 12G 显存下的最优取舍：权重约 5.5G，留约 5G 给 KV cache，32K 上下文稳定。Qwen3-14B-AWQ 权重就要 9G，KV 不足 2G，长转写稿会 OOM |

## 四、部署形态与分工

采集层留在本地、推理层放服务器，不是随意划分：

- **机房 IP 是风控重点。** 抖音、小红书对 IDC 网段极其敏感，家庭宽带 IP 干净得多。
- **CDP 模式需要图形界面。** MediaCrawler 默认开启的 `ENABLE_CDP_MODE` 靠接管真实
  Chrome 获得反检测能力，无头容器里跑不起来，等于放弃它最强的一张牌。
- **B 站是例外。** 实测服务器直连 B 站 API 只要 0.22 秒，且其接口免登录，
  因此 B 站全流程可以整体放在服务器上跑。

一律在无卡模式下做，只在跑推理时开 GPU。
