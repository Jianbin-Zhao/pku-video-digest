## E1 · 归纳模型档位横向对比

**日期** 2026-08-07 18:20
**脚本** `scripts/compare_models.py`
**问题** 归纳任务上，更大更贵的模型是否明显更好？是否值得默认用 `qwen3.8-max`？
**测试对象** B 站科技区排行榜第 1 名：《2025全球最全电脑故障解决指南》
（作者「喵喵折-好物清单」，播放 2,093,750，时长 3474 秒）
**接口** 阿里云百炼 DashScope OpenAI 兼容端点

### 轮一：仅元数据（模拟无人声视频 / ASR 失败的最坏情况）

| 模型 | 耗时 | 自评置信度 | 观察 |
| --- | --- | --- | --- |
| qwen-flash | 2.30s | 0.60 | 抓到「58 分钟、一万八千字、制作周期两个月」等具体细节 |
| qwen-plus | 3.13s | 0.55 | 与 flash 相当 |
| qwen3.7-max | 3.01s | 0.50 | 与 flash 相当 |
| qwen3.8-max | 2.59s | 0.50 | 输出与 qwen3.7-max 几乎逐字相同 |
| deepseek-v4-pro | 4.67s | 0.50 | 最慢；要点更接近照抄原文 |

### 轮二：元数据 + 文稿（模拟 ASR 成功，信息完整）

| 模型 | 耗时 | 自评置信度 | 观察 |
| --- | --- | --- | --- |
| qwen-flash | 2.17s | 0.90 | |
| qwen-plus | 3.06s | 0.85 | |
| qwen3.7-max | 2.76s | 0.85 | |
| qwen3.8-max | 2.40s | 0.85 | |
| deepseek-v4-pro | 5.44s | 0.90 | 最慢 |

### 结论

1. **横向换模型的收益极小。** 同一轮内五个模型的输出在信息量和准确度上挑不出高下，
   `qwen3.8-max` 与 `qwen3.7-max` 的输出几乎逐字相同，`qwen-flash` 反而在细节抓取上更完整。
   原因是内容摘要属于信息压缩任务而非推理任务，8B 级别的模型能力已经饱和。
2. **纵向补齐输入的收益是质变。** 同一模型在两轮之间的自评置信度从 0.50~0.60 跃升到 0.85~0.90。
3. **速度与成本差异明确。** `qwen-flash` 比 `deepseek-v4-pro` 快 1.5~2.5 倍，
   价格为 ¥0.2/百万输入 token，是本项目里性价比最优的默认选择。
4. **对本地部署可行性的推论。** 既然 flash 级模型已经够用、且档位提升无明显收益，
   那么本地 8B 量级模型很可能同样够用。这一条支撑了"纯本地部署"路线的可行性，
   待 E2 用本地 Qwen3-8B 实测验证。

### 由此确定的选型决策

- 归纳默认后端：`qwen-flash`
- 工程投入方向：优先把输入喂饱（ASR + OCR + 视觉 + 评论），而非升级文本模型档位
- 模型档位仅作为置信度低时的按需升级手段，不作为默认

## E4 · 流水线阶段耗时基线

**日期** 2026-08-07 18:50
**样本** 同 E3-a（75 秒视频，6.9 MB，720p）
**环境** 服务器 RTX 3080 Ti + 12 vCPU

| 阶段 | 耗时 | 占比 | 备注 |
| --- | --- | --- | --- |
| 榜单拉取 | 0.32s | 0.7% | B 站官方接口，直连 |
| 视频下载 | 1.81s | 4.2% | 720p，6.9 MB |
| 抽音频 | 0.35s | 0.8% | ffmpeg 转 16k 单声道 |
| 语音识别 | 11.72s | 27.0% | **其中绝大部分是模型加载**；实际推理 rtf 0.031，即 32× 实时 |
| 关键帧抽取 | 5.79s | 13.3% | 场景切变检测，抽出 24 帧 |
| 关键帧 OCR | **21.42s** | **49.3%** | 串行 24 帧，每帧约 0.9s，CPU |
| 归纳 | 2.07s | 4.8% | qwen-flash |
| 合计 | 43.49s | | |

### 结论与优化方向

1. **OCR 是首要瓶颈**，占近一半耗时。串行执行且跑在 CPU 上。
   优化手段：多线程并行（onnxruntime 推理可并发）、下调默认帧数、必要时转 GPU。
2. **ASR 的耗时是假象**。模型加载约 10 秒，批量处理时只付一次；
   真实推理速度 32× 实时，远优于官方 CPU benchmark 的 17.2×（因为跑在 GPU 上）。
   因此编排器必须复用 ASR 实例，绝不能每条视频重新加载。
3. 下载与归纳都在 2 秒级，不是瓶颈。

### E4-b OCR 并行化后的复测

**日期** 2026-08-07 18:58
**改动** `RapidOcr` 改为线程池并行，worker 数取 `min(6, CPU核数/2)`，
每个 worker 持有独立引擎实例，并把每个 onnxruntime session 的
`intra_op_num_threads` 限到 2，避免 N 个 worker 各自开满线程互相抢核。

| 阶段 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 关键帧 OCR | 21.42s | **6.39s** | **3.35× 加速** |
| 合计 | 43.49s | **27.92s** | 缩短 36% |

优化后的耗时占比变为：ASR 41.7%（几乎全是模型加载）、OCR 22.9%、关键帧 19.9%。
下一步收益最大的动作是在编排器里复用 ASR 实例，把那约 10 秒的加载摊薄到整批视频上。

**附带观察**：同一条视频、同样的输入，第二次归纳的质量明显更好，
额外识别出「系列第二期，前作为璃月高清重置」「以英文地名硬字幕呈现，无语音解说」
「结尾提示观众参与下一期地图投票」三条。这说明当输入信息充足时，
`qwen-flash` 的上限并不低，进一步支持了 E1 的选型结论。

## E5 · 编排器批量实测（场景一完整跑通）

**日期** 2026-08-07 19:19
**命令** `vspider rank --platform bili --limit 5 --category tech -j 3`
**环境** 服务器 RTX 3080 Ti + 12 vCPU，归纳走 qwen-flash
**样本** B 站科技区排行榜，实际处理第 2~6 名（第 1 名时长超过 30 分钟上限被跳过）

### 总体结果

| 指标 | 数值 |
| --- | --- |
| 成功率 | **5/5（100%）** |
| 墙钟耗时 | **78.3s** |
| 各阶段耗时之和 | 266.5s |
| 并发带来的加速 | **3.4×** |
| 处理的视频内容总时长 | 2906 秒（**48.4 分钟**） |
| 端到端处理速度 | **37× 实时** |
| 摘要置信度 | 0.85 / 0.92 / 0.92 / 0.92 / 0.92 |

单条视频从 75 秒到 1190 秒（近 20 分钟）不等，最长的一条完整跑完只用 60.58 秒。

### 阶段耗时分解（累计，跨视频并发）

| 阶段 | 累计耗时 | 占比 |
| --- | --- | --- |
| 语音识别 | 92.36s | 34.7% |
| 画面文字识别 | 63.74s | 23.9% |
| 视频下载 | 49.19s | 18.5% |
| 关键帧抽取 | 41.95s | 15.7% |
| 内容归纳 | 13.11s | 4.9% |
| 抽取音频 | 6.20s | 2.3% |

### 结论

1. **ASR 实例复用的收益兑现了**。E4 里 ASR 的 11.7 秒几乎全是模型加载，
   这一批 5 条视频只付了一次。摊薄后单条 ASR 实测 57.9× 到 96.7× 实时，
   一条 1190 秒的视频转写出 7507 字只花 26.67 秒。

2. **单条 OCR 变慢了，但这是正确的取舍**。同一条《蒙德：高清重置》，
   E4-b 单独跑是 6.39 秒，这一批里是 17.33 秒。原因是 OCR 的线程池
   此刻在和其他视频的 ffmpeg 抽帧、ASR 预处理抢 CPU。
   墙钟时间才是要优化的目标，为单条阶段耗时好看而放弃并发是本末倒置。

3. **关键帧抽取升为新的候选瓶颈**。长视频上 11~13 秒，
   因为 scene 滤镜需要解码整条视频。下一步可以先按固定间隔粗筛再在候选区间做切变检测。

4. **多源融合在这一批里再次被验证**。第 1 条依旧是无人声视频
   （语音 3 字，画面文字 663 字），第 5 条则相反（语音 2761 字，画面文字 4996 字，
   是屏幕录制的操作演示）。两条视频的主信息源完全不同，
   任何单一模态的方案都会在其中一条上失效。

5. 归纳只占 4.9%，进一步确认 E1 的结论：把预算花在输入质量上而不是更贵的模型上。

## E6 · B 站创作者接口的风控行为

**日期** 2026-08-07 19:35
**背景** 场景二（某用户今天发布的视频）依赖 `/x/space/wbi/arc/search`，
该接口带 WBI 签名风控，裸请求返回 `code=-352 风控校验失败`。

### 第一版实验（被推翻）

先按「逐项加手段」的思路做了组合矩阵，每个组合各试一次：

| 组合 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 仅 WBI 签名 | -352 | **成功** |
| + buvid | -352 | HTTP 412 |
| + dm 指纹参数 | HTTP 412 | HTTP 412 |
| + bili_ticket | -352 | HTTP 412 |
| buvid + bili_ticket | **成功** | -352 |
| buvid + ticket + _uuid | -352 | HTTP 412 |
| 全部手段 | HTTP 412 | HTTP 412 |

两轮结果几乎完全相反，同一个「裸请求」第一轮失败第二轮却成功。
**这个实验设计是错的**：它默认了结果由参数组合决定，
但两轮的矛盾说明存在一个没有被控制的变量。

### 第二版实验（改测成功率）

改成每个配置连发 6 次、间隔 3 秒，配置之间冷却 25 秒，统计通过比例：

| 配置 | 成功率 | 失败分布 |
| --- | --- | --- |
| 仅 WBI 签名 | 3/6 | -352 ×3 |
| + buvid | 0/6 | -352 ×4, 412 ×2 |
| + buvid + bili_ticket | 1/6 | -352 ×3, 412 ×2 |
| + buvid + ticket + dm 参数 | 2/6 | -352 ×2, 412 ×2 |

### 结论

1. **主导变量是按 IP 的请求频率，不是指纹参数**。没有任何配置能稳定通过，
   成功率在 0%~50% 之间波动，且随着整轮测试的进行整体下滑（额度被逐步透支）。

2. **`dm_img_*` 这组 WebGL 指纹参数不是必需的**，加上以后反而更容易触发 HTTP 412。
   这与网上大量教程的说法相反，因此从实现中移除。

3. **单次请求必然不可靠，重试是唯一出路**。据此实现：
   最多 5 次、从 2 秒起指数退避，且每次重试都换一份新的匿名身份
   （buvid / bili_ticket 全部重新申领）——触发风控后同一个 buvid 会被短暂拉黑，
   沿用它重试只是白等。加上重试后实测稳定拿到结果。

4. **登录态才是根本解**。这正是 MediaCrawler 采用扫码登录 + 真实浏览器
   会话的原因。实现上支持 `.env` 里的 `BILI_COOKIE`，
   带 SESSDATA 时跳过匿名身份轮换。

### 顺带确认：不是 IP 归属地问题

服务器出口是宁夏联通 116.172.93.87，本机是甘肃电信 27.225.173.87，
两边表现一致（都会 412）。所以不需要为这个接口把采集挪回本地，
之前定的混合架构在 B 站上没有额外收益——真正需要本地浏览器的是
小红书和抖音，理由是登录态而非 IP。

## E8 · 抽帧策略与视频编码格式

**日期** 2026-08-07 20:10
**起因** E7 发现关键帧抽取升为最大单项（23.37s，占单条 37.8%）。
**样本** 极客湾《理想马赫 M100 深度体验》BV1HDNd65EkV，632 秒，720p。

### 为什么这样设计对比

抽帧不是目的，喂给 OCR 读出画面文字才是。所以**只比速度会得出错误结论**：
一个快但漏字的策略是负收益。因此每种策略都跑完整的 OCR，
同时记录三个量——抽帧耗时、OCR 耗时、识别出的有效字数（去重后）。
帧数统一固定为 24，否则「抽得多所以字多」会把结论污染掉。

三种策略：

| 策略 | 做法 | 预期 |
| --- | --- | --- |
| scene | ffmpeg 的 scene 滤镜按画面变化程度筛选 | 语义最准，但要整片解码 |
| iframe | 读视频自带的关键帧位置 | 编码器本就在镜头切变处插 I 帧，应该近乎免费 |
| interval | 按固定间隔均匀采样 | 最快，但可能采到重复画面 |

### 第一轮：iframe 实现是坏的

| 策略 | 抽帧 | OCR | 帧数 | 有效字数 |
| --- | --- | --- | --- | --- |
| iframe | 39.87s | 13.27s | 24 | 2857 |
| scene | 21.70s | 11.24s | 24 | 4010 |
| interval | 1.69s | 13.59s | 24 | 2857 |

iframe 比 scene 还慢，且字数与 interval **完全一致**（都是 2857）。
这个巧合暴露了问题：iframe 实际上什么也没抽到，静默退化到了 interval 兜底，
而那 38 秒的探测纯属白花。

**根因**（用裸 ffprobe 复现）：原实现用
`-skip_frame nokey -show_entries frame=pts_time`，两个坑同时踩上了。
一是 AV1 流下 `pts_time` 返回空值，二是 libdav1d 根本不理会 `-skip_frame`——
它老老实实把整条视频解码完，吐出全部 18948 帧（632s × 30fps）。

**修法**：改读**包**而不是帧。关键帧标记写在包的 flags 里（含 "K"），
包层面只需要解复用、完全不解码：

```
ffprobe -select_streams v:0 -show_entries packet=pts_time,flags -of csv=p=0
```

### 第二轮：修复后（AV1 源）

| 策略 | 抽帧 | OCR | 合计 | 有效字数 |
| --- | --- | --- | --- | --- |
| **iframe** | **2.22s** | 13.11s | **15.33s** | **4378** |
| scene | 22.97s | 12.21s | 35.18s | 4010 |
| interval | 1.77s | 12.01s | 13.78s | 2857 |

**iframe 在两个维度上同时胜出**：比 scene 快 10.3 倍，字数还多 9%。
比 interval 只多花 0.45 秒，字数却多 53%。

字数反超 scene 有点反直觉，原因是 scene 滤镜只在「变化剧烈」处触发，
一段长时间静止的图表或代码演示只会被采到一次；
而 I 帧是编码器按 GOP 周期强制插入的，即使画面静止也会定期出现，
反而覆盖得更均匀。

### 第三轮：编码格式的影响

同一条视频改用 H.264 重新下载后复测：

| 策略 | AV1 抽帧 | H.264 抽帧 | 加速 |
| --- | --- | --- | --- |
| iframe | 2.22s | 1.46s | 1.5× |
| scene | 22.97s | 5.95s | **3.9×** |
| interval | 1.77s | 1.51s | 1.2× |

代价是体积从 28.5 MB 涨到 46.1 MB（+61%）。单条 A/B 测下载耗时几乎不变
（16.68s vs 16.94s），看起来是白拿的好处，于是当时把下载格式改成了优先 avc1。

### 第四轮：批量实测推翻了第三轮的结论

把改动放回完整流水线跑五条视频，和 E5 的基线对比：

| 阶段 | E5 基线（AV1） | 改 H.264 后 | 撤回改动（AV1） |
| --- | --- | --- | --- |
| 视频下载 | 49.19s | **80.07s** | 70.70s |
| 关键帧抽取 | 41.95s | 7.81s | **7.77s** |
| 画面文字识别 | 63.74s | 61.09s | 44.70s |
| 各阶段合计 | 266.54s | 260.60s | **222.13s** |
| 墙钟 | 78.3s | 75.4s | **68.2s** |

**单条 A/B 测不出来的东西，在批量里暴露了**：三路并发下载共享带宽时，
多出来的 61% 体积是要还的，下载累计从 49.19s 涨到 80.07s，
而抽帧只省下约 4 秒。净结果是负的。

更关键的是「关键帧抽取」两栏几乎一模一样（7.81s vs 7.77s），
这直接证明 **iframe 策略根本不吃编码格式**——它只解复用、不解码。
第三轮那个「H.264 解码快 3.9 倍」的优势，在主路径上压根兑现不了。

因此**撤回下载格式的改动**，恢复为不限定编码。

需要说明的是，下载耗时在不同批次之间波动很大（同为 AV1 的两次跑分别是
49.19s 和 70.70s），所以跨批次的墙钟对比只能作参考。
这一轮真正可靠的结论是阶段内的对比：关键帧抽取稳定在 7.8 秒左右，
且与编码格式无关。

### 第五轮：多样本复验（推翻了前面的质量结论）

前四轮全部只用了一条视频。这不足以支撑「改默认策略」这种决定——
视频的镜头节奏、有无硬字幕、编码参数差异极大，单条样本的结论很可能只是过拟合。

于是用 `scripts/fetch_corpus.py` 跨六个分区（科技 / 音乐 / 鬼畜 / 生活 /
游戏 / 美食，刻意选镜头节奏差异最大的）建了 12 条的语料库，
随机抽 8 条（种子 42）复跑：

| 样本 | 时长 | iframe 抽帧 / 字数 | scene 抽帧 / 字数 | interval 抽帧 / 字数 |
| --- | --- | --- | --- | --- |
| BV1sGZbY6EoW | 75s | 0.73s / 467 | 5.78s / **663** | 1.20s / 411 |
| BV15gZzYXE4N | 310s | 0.91s / 345 | 6.92s / 291 | 1.56s / **394** |
| BV11PZsY8EtB | 164s | 0.89s / **3523** | 3.73s / 1670 | 1.59s / 3508 |
| BV1DtZCYdEH8 | 356s | 1.08s / 2544 | 8.14s / **2619** | 1.70s / 2387 |
| BV1DDZHYhE59 | 323s | 1.00s / **404** | 12.09s / 241 | 1.56s / 364 |
| BV1zKZrYAEi8 | 41s | 0.45s / 175 | 1.86s / **292** | 0.59s / 184 |
| BV1JcZtYFEDq | 70s | 0.71s / 17 | 4.98s / 28 | 1.34s / **33** |
| BV1nwZEYqE2B | 129s | 0.87s / 378 | 2.41s / **381** | 1.35s / 294 |

汇总：

| 策略 | 抽帧中位 | 抽帧均值 | 字数中位 | 字数均值 | 单样本夺冠 |
| --- | --- | --- | --- | --- | --- |
| **iframe** | **0.88s** | **0.83s** | 391 | 982 | 2/8 |
| scene | 5.38s | 5.74s | 336 | 773 | 4/8 |
| interval | 1.46s | 1.36s | 379 | 947 | 2/8 |

**结论必须修正**：

1. **速度优势是真实且稳健的**。iframe 均值 0.83s vs scene 5.74s，快 **6.9 倍**，
   在全部 8 条样本上无一例外。

2. **「iframe 字数更多」这个结论不成立**。三种策略的字数均值分别是
   982 / 773 / 947，iframe 相对 interval 只有 1.04×，落在噪声范围内；
   按单样本夺冠次数算，scene 反而以 4/8 领先。
   第二轮那个「iframe 比 scene 多 9%、比 interval 多 53%」完全是样本特性，
   换一批样本就消失了。

3. **scene 的表现两极分化**：单样本夺冠最多（4/8），但均值最低（773）。
   原因是它在少数样本上塌得很惨（BV11PZsY8EtB：1670 vs iframe 的 3523）——
   那类视频画面变化平缓，scene 触发不足，长时间静止的图表只被采到一次。
   它赢的时候赢一点，输的时候输很多。

### 最终结论

1. 默认策略定为 **iframe**，但**理由是速度而不是质量**：它比 scene 快 6.9 倍，
   而三种策略的文字产出在统计上没有显著差异。
   实际收益：关键帧抽取累计从 41.95s 降到 7.77s（**5.4×**）。
2. 下载格式**维持不限定编码**。中途改成优先 H.264，被批量实测推翻后撤回。
3. 方法论上三条教训，第三条代价最大：
   - **「只测速度」会选错策略**。所以基准里必须带上 OCR 字数这个质量指标。
   - **单条测试会漏掉资源争抢**。H.264 在单条 A/B 下看着免费，
     放进三路并发就现原形。优化必须在真实并发下复测。
   - **单样本得出的质量结论不可信**。前四轮基于一条视频得出的
     「iframe 字数也更多」，在 8 样本上直接消失。
     结论对了（选 iframe），但理由是错的——如果当初 scene 在那条样本上
     恰好胜出，就会做出错误的选型。**幸存的正确结论不等于可靠的方法。**

## E10 · 本地 GPU 归纳落地（vLLM + Qwen3-8B-AWQ）

**日期** 2026-08-08 22:45
**目的** 把归纳从云 API 搬到服务器本地，正面回应「尽量本地部署」。
**环境** RTX 3080 Ti 12 GB，vLLM 0.26.0（独立 venv，torch 2.11，与主环境隔离），
Qwen3-8B-AWQ（5.7 GB，awq_marlin 内核）。

### 部署踩坑

1. **conda 建环境卡死**：`conda create` 在本机镜像上 solve repodata 卡了 8 分钟无进展，
   改用 `python -m venv` 由 base python 直接建，pip 走已配好的阿里云镜像，秒级完成。
2. **`pkill -f api_server` 自杀**：kill 命令行里含 `api_server` 字面量，
   被自己的 `-f` 正则命中，连发起命令一起杀掉（表现为 exit -1、无输出）。
   改用 `pkill -f 'api[_]server'` 的括号技巧，且命令里任何位置都不出现该字面量。
   （这条其实 EXPERIMENTS「环境与踩坑」里早有记录，又踩了一次。）
3. **12 GB 显存放不下「大 KV」**：vLLM 0.26 固定占用约 6.1 GB
   （权重 5.71 + 峰值激活 0.19 + CUDAGraph 0.09 + 非 torch 0.08）。
   起初 `--gpu-memory-utilization 0.55`（6.6 GB）导致
   `Available KV cache memory: -0.58 GiB` 直接起不来。
4. **flag 改名**：`--disable-log-requests` 在 0.26 改成 `--no-enable-log-requests`。

### 两档显存配置

| 配置 | vLLM util | ASR 设备 | KV cache | 说明 |
| --- | --- | --- | --- | --- |
| A | 0.85（9.9 GB） | CPU | 3.92 GiB | LLM 独占 GPU，ASR 让给 CPU |
| B | 0.70（8.1 GB） | cuda:0 | 约 2 GiB | LLM 与 ASR 同卡共存 |

配置 A 实测（快手 3 条，`understand.py --profile gpu --device cpu`）：
**3/3 成功，墙钟 79.6s**。归纳全部由本地 Qwen3-8B 产出，结构化 JSON 正常，
内容与 qwen-flash 版一致（识别出「三步涨流量干货」「农民视角改编《谁》」等）。
**内容归纳累计仅 3.81s**——本地 8B 归纳速度完全够用。
代价是 ASR 落到 CPU，语音识别累计 118.85s（占 80.7%），成为该配置下的瓶颈。

### 质量对照（本地 Qwen3-8B vs 云 qwen-flash，回应 E2 待办）

同一批快手视频，两者的一句话摘要与要点在信息量、准确度上无实质差异。
差异只在**置信度自评**：本地 Qwen3-8B 给 0.60~0.70，云 qwen-flash 给 0.85。
这与 E1 的结论一致——归纳是信息压缩任务，8B 级别能力已饱和，
换模型收益极小，瓶颈始终在输入是否喂饱。**因此「纯本地部署」在质量上可接受，
E2 的假设得到验证。**

### 配置 B（LLM 与 ASR 同卡）被否

想把 ASR 拉回 GPU 消除配置 A 的 CPU 瓶颈，试了 util 0.70：
KV cache 只剩 1.17 GiB，16K 上下文需 1.69 GiB 直接起不来，估计最大只到 8496 token；
即便降到 8K 也只是勉强够、且运行期并发一上就可能 OOM。这条对「稳定」不利，**放弃**。
结论：12 GB 卡上 LLM 与 ASR 无法稳定同卡，ASR 让给 CPU 是当前硬件下的稳妥取舍。
换 ≥16 GB 显卡即可两者同卡、ASR 回到 GPU 速度。

### 配置 A 的 B 站全链路收尾（零外部 API）

`vspider rank --platform bili --limit 2 --profile gpu --device cpu`，服务器直连：
发现→下载→ASR(CPU)→OCR(CPU)→归纳(本地 vLLM)全通，**2/2 成功**。
两条分别 420s / 686s 的长视频，本地 Qwen3-8B 准确归纳出「聪明猫靠观察而非本能
解决问题」「用雨滴入湖的比喻探讨死亡」，置信度 0.70 / 0.80，内容归纳累计仅 4.04s。
瓶颈是 CPU 上的 ASR：累计 342.84s（占 92.4%），墙钟 281.6s——长视频在 12 GB
卡上被迫用 CPU 转写就是这个代价。**功能与本地部署目标已达成；追求速度时用 api 档
或换更大显存的卡。**

至此本地 GPU 部署这一大阶段完成：三个模型（SenseVoice / RapidOCR / Qwen3-8B）
全部本地运行，归纳彻底摆脱云 API。
